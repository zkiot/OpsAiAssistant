# 生产环境常见问题知识库

> 用途：作为运维知识库检索系统（RAG）的知识源文档，涵盖 Redis 故障处理、MySQL 故障处理、日常巡检规范三大部分。每个二级标题下的内容相对独立完整，适合按段落切分入库。

## 一、Redis 故障处理

### 1.1 连接数耗尽 / 无法建立新连接

**现象：** 应用报 `Cannot get Jedis connection`、`Connection refused`、`ERR max number of clients reached`。

**排查步骤：**
1. `redis-cli info clients` 查看 `connected_clients` 当前值，对比 `maxclients` 配置上限。
2. `redis-cli client list` 查看当前连接列表，按 `addr` 分组统计，定位是否是某个应用实例连接数异常暴涨（常见于连接池配置错误，比如没有设置最大连接数、或者代码里没有正确归还连接）。
3. 检查应用端连接池配置（如 Jedis/Lettuce 的 `maxTotal`、`maxIdle`），排查是否存在连接泄漏（获取连接后未在 finally 块中关闭）。

**处理方式：**
- 临时缓解：调大 `maxclients` 配置（`CONFIG SET maxclients 10000`），只能救急，不解决根因。
- 根治：修复应用端连接池配置或连接泄漏代码；如果是短连接场景，改造为连接池复用。

### 1.2 内存不足 / OOM

**现象：** `redis-cli info memory` 显示 `used_memory` 接近 `maxmemory`，写入命令报错 `OOM command not allowed`。

**排查步骤：**
1. `redis-cli info memory` 查看 `used_memory`、`maxmemory`、`mem_fragmentation_ratio`（内存碎片率，正常应在 1.0-1.5 之间，过高说明碎片严重）。
2. `redis-cli --bigkeys` 扫描大 key，定位是否有异常大的 hash/list/set 占用了大量内存。
3. 检查 `maxmemory-policy` 配置：如果是 `noeviction`（默认值），内存满了会直接拒绝写入而不是淘汰旧数据；生产环境作为缓存使用时，通常应设置为 `allkeys-lru` 或 `volatile-lru`。

**处理方式：**
- 短期：手动清理明确无用的大 key（`DEL` 或 `UNLINK`，`UNLINK` 是异步删除，大 key 用它避免阻塞主线程）。
- 中期：调整 `maxmemory-policy` 为合适的淘汰策略。
- 长期：评估是否需要扩容（加内存或做 Redis Cluster 分片），从业务侧排查是否存在不合理的大 key 设计（比如把整个用户列表存进一个 hash）。

### 1.3 主从复制延迟 / 数据不一致

**现象：** 从库读到的数据比主库旧，`redis-cli info replication` 里 `master_repl_offset` 和从库的 `slave_repl_offset` 差距很大。

**排查步骤：**
1. 主库执行 `info replication`，查看每个从库的 `lag`（延迟秒数）。
2. 检查网络带宽是否打满（主从复制走 TCP，大量写入 + 网络带宽不足会导致复制积压）。
3. 检查从库是否在执行耗时的阻塞命令（比如 `KEYS *`、大范围的 `SCAN` 未加限制），阻塞了复制线程处理。
4. 检查主库是否有 `bgsave`/`aof rewrite` 正在进行，这类持久化操作会占用 CPU/IO，间接影响复制速度。

**处理方式：**
- 应用层：读从库的场景增加对延迟的容忍设计，关键业务（如支付）强制读主库。
- 运维层：优化网络带宽，避免在从库执行高危命令，合理安排持久化任务的时间窗口（避开业务高峰）。

### 1.4 缓存穿透 / 击穿 / 雪崩

**缓存穿透：** 查询根本不存在的数据（比如恶意攻击用不存在的ID查询），请求绕过缓存直接打到数据库。
- 处理：对查询结果为空的 key 也缓存一个短期的空值（`""` 或占位符）；引入布隆过滤器提前拦截明显不存在的 key。

**缓存击穿：** 某个热点 key 突然过期，大量并发请求同时穿透到数据库。
- 处理：热点 key 设置永不过期（后台异步更新）；或者用互斥锁（`SETNX`）保证只有一个请求去数据库加载数据，其他请求等待或返回旧值。

**缓存雪崩：** 大量 key 在同一时间集中过期，或者 Redis 实例整体宕机，瞬间流量全部打到数据库。
- 处理：给缓存过期时间加随机抖动（比如基础过期时间 + 随机的 0-300 秒），避免同时失效；Redis 本身做高可用（哨兵/集群），避免单点故障导致缓存整体不可用。

### 1.5 持久化相关故障

**AOF/RDB 文件损坏导致重启失败：**
- `redis-check-aof --fix appendonly.aof` 修复 AOF 文件；`redis-check-rdb dump.rdb` 检查 RDB 文件。
- 修复有数据丢失风险，优先从副本或备份恢复，AOF/RDB 修复工具作为最后手段。

**`bgsave` 频繁失败：**
- 检查磁盘剩余空间（`df -h`），Redis 生成 RDB 快照需要额外磁盘空间。
- 检查内存是否充足：`bgsave` 用 `fork` 子进程复制内存页表，内存不足或开启了 overcommit 限制会导致 fork 失败。

## 二、MySQL 故障处理

### 2.1 连接数耗尽

**现象：** 应用报 `Too many connections`。

**排查步骤：**
1. `SHOW STATUS LIKE 'Threads_connected';` 查看当前连接数，对比 `SHOW VARIABLES LIKE 'max_connections';` 上限。
2. `SHOW PROCESSLIST;` 查看当前连接列表，重点看 `Time` 字段异常大、`Command` 为 `Sleep` 的连接是否大量堆积（说明应用没有正确关闭/归还连接）。
3. 排查是否是慢查询导致连接长时间不释放，进而占满连接池。

**处理方式：**
- 临时：`SET GLOBAL max_connections = xxx;` 应急调大上限（需要评估内存承受能力，每个连接会占用一定内存）。
- 根治：修复应用连接池配置和慢查询问题；杀掉异常挂起的连接 `KILL <id>;`。

### 2.2 慢查询 / CPU 飙高

**排查步骤：**
1. 开启慢查询日志（`slow_query_log = ON`，`long_query_time` 设置合理阈值如 1 秒），定位具体慢 SQL。
2. 用 `EXPLAIN` 分析执行计划，重点看 `type`（避免 `ALL` 全表扫描）、`key`（是否命中索引）、`rows`（预估扫描行数）。
3. `SHOW PROCESSLIST;` 结合 `SHOW ENGINE INNODB STATUS;` 看是否有长事务、锁等待导致的连锁反应。

**处理方式：**
- 补充合适的索引，或改写 SQL 避免索引失效（隐式类型转换、索引列上做函数运算等）。
- 大表深分页场景，改用基于游标（记录上次最大ID）的方式代替 `LIMIT offset, count`。
- 历史数据做归档，减小单表数据量。

### 2.3 主从复制延迟

**现象：** 从库 `SHOW SLAVE STATUS\G` 里 `Seconds_Behind_Master` 持续增大。

**排查步骤：**
1. 确认是否为单线程复制（MySQL 5.6 之前默认单线程回放 binlog，大事务或高并发写入场景容易延迟），检查是否已开启并行复制（`slave_parallel_workers`）。
2. 检查从库自身是否有大量只读查询占用资源，影响复制回放。
3. 检查主库是否有大事务（大批量 update/delete），大事务在从库上是单条回放，耗时会显著增加。

**处理方式：**
- 开启基于组提交的并行复制（MySQL 5.7+ 的 `slave_parallel_type = LOGICAL_CLOCK`）。
- 业务侧避免大事务，拆分成多个小批次操作。
- 关键业务读写分离时，对延迟敏感的查询强制走主库。

### 2.4 死锁

**现象：** 应用报 `Deadlock found when trying to get lock`。

**排查步骤：**
1. `SHOW ENGINE INNODB STATUS;` 里的 `LATEST DETECTED DEADLOCK` 部分能看到最近一次死锁的两个事务分别持有和等待的锁。
2. 分析两个事务的 SQL 执行顺序，找出交叉加锁的模式（典型场景：两个事务以不同顺序更新同一批行）。

**处理方式：**
- 统一同一批业务操作中多行更新的加锁顺序（比如都按主键从小到大的顺序更新）。
- 缩小事务粒度，尽快提交，减少锁持有时间。
- 应用层捕获死锁异常后做有限次数的自动重试（死锁是 MySQL 主动检测并回滚其中一个事务，重试通常能成功）。

### 2.5 磁盘空间不足

**现象：** 写入报错 `Disk full`，MySQL 可能直接停止响应写请求甚至只读。

**排查步骤：**
1. `df -h` 确认磁盘使用率，定位是数据文件、binlog 还是慢查询日志占用过大。
2. 检查 binlog 保留策略（`expire_logs_days` 或 `binlog_expire_logs_seconds`），是否设置了自动清理。
3. 检查是否有历史大表/大量碎片数据未清理（`OPTIMIZE TABLE` 前先评估锁表影响）。

**处理方式：**
- 紧急清理过期 binlog：`PURGE BINARY LOGS BEFORE '2026-01-01 00:00:00';`。
- 设置合理的 binlog 自动过期策略，避免再次积累。
- 长期：评估磁盘扩容或历史数据归档策略。

### 2.6 主从切换 / 高可用相关

**主库宕机后的处理流程：**
1. 确认主库真实状态（是否为网络分区导致的误判，避免脑裂）。
2. 选取 binlog 位点最新（数据最全）的从库提升为新主库。
3. 其余从库指向新主库重新建立复制关系。
4. 应用配置/域名指向切到新主库，恢复写入。

**建议：** 生产环境用 MHA、Orchestrator 或云厂商托管的高可用方案自动化这个流程，减少人工介入的响应时间和出错概率。

## 三、日常巡检规范

### 3.1 巡检目标与频率

| 巡检类型 | 频率 | 覆盖范围 |
|---|---|---|
| 基础资源巡检 | 每日 | CPU/内存/磁盘/网络 |
| 中间件巡检 | 每日 | Redis/MySQL/Kafka/RocketMQ 等运行状态 |
| 安全巡检 | 每周 | 异常登录、端口暴露、证书有效期 |
| 容量评估 | 每月 | 磁盘增长趋势、连接数增长趋势、是否需要扩容 |
| 灾备演练 | 每季度 | 主从切换演练、备份恢复演练 |

### 3.2 服务器基础指标巡检项

- **CPU**：使用率是否长期超过 70%（持续高位需要关注是否有异常进程或需要扩容）；`load average` 是否显著超过 CPU 核数。
- **内存**：可用内存是否充足；`swap` 使用是否异常增长（频繁 swap 说明物理内存不足，会严重拖慢性能）。
- **磁盘**：各分区使用率是否超过 80%（预留缓冲空间，避免写满导致服务异常）；磁盘 IO 等待（`iowait`）是否过高。
- **网络**：网卡流量是否接近带宽上限；是否有异常的连接数或丢包率。

### 3.3 Redis 巡检项

- `info replication` 确认主从关系正常，无异常延迟。
- `info memory` 确认内存使用率、碎片率在合理范围。
- `info stats` 查看 `expired_keys`、`evicted_keys` 是否异常，`evicted_keys` 持续增长说明内存不足触发了淘汰，需要关注。
- 确认持久化（AOF/RDB）任务正常执行，无失败记录。
- 慢日志检查：`SLOWLOG GET 10` 查看最近的慢命令，定位是否有不合理使用（如线上跑 `KEYS *`）。

### 3.4 MySQL 巡检项

- 主从复制状态：`SHOW SLAVE STATUS\G` 确认 `Slave_IO_Running`、`Slave_SQL_Running` 均为 `Yes`，`Seconds_Behind_Master` 在可接受范围。
- 慢查询数量趋势：对比历史基线，是否有明显增长。
- 连接数使用率：`Threads_connected` / `max_connections` 是否处于健康区间（建议不超过 70%）。
- 表空间增长趋势：核心大表的增长速度是否符合预期，是否需要提前规划归档/分表。
- 备份任务：确认每日备份任务正常完成，且定期做恢复演练验证备份可用性（"有备份"不等于"能恢复"，必须定期验证）。

### 3.5 巡检发现问题后的处理流程

1. **分级**：按影响范围和紧急程度分级（比如 P1 影响核心业务立即处理、P2 需要在24小时内跟进、P3 记录到下个迭代优化）。
2. **登记**：所有巡检发现的异常统一登记到工单系统，避免口头交接遗漏（对应我们运维助手里的工单创建工具）。
3. **闭环**：明确责任人和处理时限，处理完成后回填结果，形成可追溯的处理记录。
4. **沉淀**：典型故障处理完成后，补充到知识库（也就是本文档这类内容），供下次同类问题快速参考，并推动能自动化检测的项目转为自动巡检脚本，减少重复人工排查。

### 3.6 常见误区提醒

- **只看"是否报警"，不看趋势**：很多问题在报警阈值触发前就有增长趋势（比如磁盘使用率持续攀升），巡检应关注趋势而不仅是阈值瞬时状态。
- **备份从不做恢复演练**：备份文件损坏或备份策略本身有问题，只有在真正需要恢复时才会发现，必须定期演练。
- **巡检项一成不变**：新上线的服务/中间件要及时补充进巡检范围，避免巡检覆盖面滞后于实际架构变化。
